# 漏斗与留存

「漏斗分析」看有多少人按顺序做完了几件事，每一步掉了多少人。「留存分析」看新来的人过几天还回不回来。

两个页面都在「埋点分析」菜单下，都按人统计，不按设备。

![漏斗分析页，上面是漏斗步骤，左下是转化漏斗图，右下是步骤明细](/screenshots/track/track-funnel.png)

## 人怎么算

漏斗和留存用同一种办法认人：

- 设备调用过 `identify` 关联到业务用户的，按业务用户算。同一个用户的几台设备合成一个人。
- 没有关联过的设备按匿名 ID 算，一台设备一个人。

关联对之前的事件也生效。一台设备登录以后，它登录前上报的事件也算在这个用户名下。

数据概览里的 UV 只按设备去重，所以这两页的人数和 UV 对不上是正常的。`identify` 的用法见[安装与初始化](/track/install#识别用户)。

## 漏斗怎么算

| 规则 | 说明 |
| --- | --- |
| 步骤 | 2 到 5 步，每一步是一个事件，不能重复 |
| 顺序 | 要按步骤的先后发生，中间可以夹着别的事件 |
| 第一步 | 取每个人在时间范围内第一次发生的那一次 |
| 后面的步骤 | 要在上一步之后的转化窗口内发生，超出窗口不算 |
| 转化窗口 | 1 小时、24 小时或 7 天，默认 24 小时 |
| 时间范围 | 今天、近 7 天或近 30 天，从当地时区的 0 点算起 |

转化窗口限的是相邻两步之间的间隔，不限从第一步到最后一步的总时长。

举个例子，三步漏斗选 24 小时，第二步在第一步后 20 小时发生，第三步再过 20 小时发生，这个人算走完了。

第一步只取第一次。一个人做了第一步没有往下走，隔了超过转化窗口又重新走了一遍，后面的步骤不计他。

先后按事件的发生时间比。两步的发生时间完全相同时，按顺序成立算。

## 做一个漏斗

<div class="ms-steps">

### 选应用、时间范围和转化窗口

都在页面顶部。应用和时间范围沿用其他埋点页面上次选的值。

### 配步骤

在「漏斗步骤」里给每一步选一个事件。点「添加步骤」加到最多 5 步，用上移、下移调顺序，最少留 2 步。

### 点「查询」

左边是「转化漏斗」图，右边是「步骤明细」表。

</div>

步骤明细有三个数：

| 列 | 含义 |
| --- | --- |
| 人数 | 走到这一步的人数 |
| 相对上一步转化率 | 这一步的人数除以上一步的人数。第一步没有这个数 |
| 总转化率 | 这一步的人数除以第一步的人数 |

有几点要知道：

- 事件下拉来自这个应用的事件定义，最多列 500 个。事件上报过一次才会出现在这里，见[接入管理](/track/apps#事件定义)。
- 步骤不会保存，刷新页面后要重新配。切换应用会清空查询结果。
- 所有步骤的人数都是 0 时，页面显示「窗口内无转化数据」。
- 结果在后端缓存 45 秒，条件不变时马上重查拿到的是同一份。

## 留存怎么算

留存分析看的是新客留存：把新来的人按第一次活跃的日期分组，看每一组在之后每一天还有多少人活跃。

| 规则 | 说明 |
| --- | --- |
| 活跃 | 当天有任意一条事件 |
| 新客 | 在所选的时间范围内第一次活跃，并且时间范围开始前的 30 天里没有活跃过 |
| 时间范围 | 近 7 天、近 14 天或近 30 天，都包含今天 |
| 切天 | 按当地时区的 0 点，时区怎么设见[看板怎么统计](/track/#看板趋势) |

往前只回看 30 天。30 天以前来过、之后一直没来的老用户，再回来时会算成新客。

## 读留存网格

选好应用和时间范围，点「查询」后出现「新客留存网格」。

![留存分析页的新客留存网格，每行是一天的新客，格子颜色越深留存率越高](/screenshots/track/track-retention.png)

- 每一行是一天的新客，第一列是日期和这一天的新客人数。没有新客的日期不占行。
- D+0 是第一次活跃的当天，所以总是 100%。D+1 是第二天，往后类推。
- 格子里的留存率，等于这一天还活跃的人数除以这一组的新客人数。鼠标停在格子上显示人数。
- 颜色越深留存率越高。还没到的日子显示「·」，按浏览器所在时区的日期判断。

留存算的是当天有没有回来，不要求中间每天都来。D+3 活跃的人，D+1 和 D+2 可以没来过。

## 权限

| 权限 | 能做什么 |
| --- | --- |
| `sys:track-funnel:list` | 打开漏斗分析并查询 |
| `sys:track-retention:list` | 打开留存分析并查询 |
| `sys:track-app:list` | 加载页面顶部的应用下拉，以及漏斗的事件下拉 |

只能查本租户的应用。

## 接口

两个接口都在 `/system/track` 下面，都是 GET，要登录。

| 路径 | 权限 | 参数 |
| --- | --- | --- |
| `/funnel` | `sys:track-funnel:list` | `appKey` `steps` `days` `windowHours` |
| `/retention` | `sys:track-retention:list` | `appKey` `days` |

`/funnel` 的参数：

| 参数 | 说明 |
| --- | --- |
| `steps` | 事件名用英文逗号隔开，2 到 5 个，不能重复 |
| `days` | 默认 7，可取 1 到 30，超出范围报错 |
| `windowHours` | `1` `24` `168` 之一，默认 `24` |

返回里的 `steps` 按传入的顺序排，每项有 `eventName` 和 `count`。转化率不在返回里，要自己用 `count` 算。

`/retention` 的 `days` 默认 7。超过 30 时按 30 查，不报错，返回里的 `clamped` 是 `true`。

`/retention` 返回这些字段：

| 字段 | 说明 |
| --- | --- |
| `rows` | 每个有新客的日期一项，按日期升序 |
| `rows[].cohortDate` | 新客日期，格式 `yyyy-MM-dd` |
| `rows[].cohortSize` | 这一天的新客人数 |
| `rows[].retained` | 键是第几天，从 `"0"` 开始，值是那一天活跃的人数。没人活跃的天没有键 |
| `days` | 实际生效的天数 |
| `zone` `today` | 切天用的时区，和这个时区里的今天 |
| `clamped` | 请求的天数超过上限、被改成 30 时是 `true` |
