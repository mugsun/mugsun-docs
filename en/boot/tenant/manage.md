# Tenants and plans

The platform super admin maintains tenants and plans under the Tenant Operations menu of the admin console.

## Create a tenant

Open Tenant Operations → Tenants and click "Add tenant". Fill in the name, contact, account limit, expiry time and plan. On save, the system generates a 6-digit tenant code and creates the following defaults for the tenant:

- a department with the same name as the tenant;
- a default post with the code `default`;
- an admin role with the code `admin` and the data scope "all data";
- an admin user with the username `admin`, whose initial password comes from `mugsun.security.init-password`.

A tenant admin signs in with the tenant code, username and password on the sign-in page. Leaving the tenant code empty means the platform tenant.

## Disable, expiry and account limit

- After a tenant is disabled, its users cannot sign in. Users who are already signed in are rejected on their next call to an endpoint under `/system`.
- Once the expiry time passes, the tenant behaves as if it were disabled.
- An account limit of `-1` means no limit. When the limit is reached, adding a user asks you to contact the administrator.

The platform tenant cannot be disabled or deleted. Deleting any other tenant also soft-deletes its users, departments, posts and roles.

## Plans

A plan limits which features a tenant can use. Create a plan under Tenant Operations → Tenant Packages, select its feature menus, and then choose the plan on the tenant.

The plan is enforced on the server, not only by hiding menus. When a tenant calls an endpoint outside its plan, the response is 403 with "该功能不在您的套餐内，请联系管理员开通" (the feature is not in your plan). Changes to a plan or tenant made in the console take effect immediately. A tenant without a plan is not restricted.

## Platform endpoints

Endpoints for tenants, plans, tenant data sources, online users, storage settings, scheduled jobs and other platform resources are open only to the platform super admin. Menus, dictionaries and parameters are global settings; tenants can read them but cannot change them.

When the `X-Tenant-Id` request header differs from the tenant of the login session, the request is rejected with "无权跨租户操作" (cross-tenant access denied).

## See it work

After you create a tenant named 示例门店 on the plan 基础版, the list shows a new row with a code generated by the system.

![Tenant list](/screenshots/tenant/tenant-list.png)

Check the tenant and its defaults with these queries. Replace `226994` with the actual tenant code:

```sql
SELECT tenant_code, tenant_name, status, account_count, package_id
FROM sys_tenant
WHERE is_deleted = 0
ORDER BY tenant_code;

SELECT 'dept' AS kind, dept_name AS name FROM sys_dept WHERE tenant_id = '226994' AND is_deleted = 0
UNION ALL SELECT 'post', post_name FROM sys_post WHERE tenant_id = '226994' AND is_deleted = 0
UNION ALL SELECT 'role', role_code FROM sys_role WHERE tenant_id = '226994' AND is_deleted = 0
UNION ALL SELECT 'user', username FROM sys_user WHERE tenant_id = '226994' AND is_deleted = 0;
```

The second query returns four rows: the department 示例门店, the post 默认岗位, the role `admin` and the user `admin`. Then look at the plan bound to each tenant:

```sql
SELECT t.tenant_code, p.name, p.menu_keys
FROM sys_tenant t
LEFT JOIN sys_tenant_package p ON p.id = t.package_id AND p.is_deleted = 0
WHERE t.is_deleted = 0
ORDER BY t.tenant_code;
```

The `menu_keys` of 基础版 is `User,Dept`. Sign in as that tenant's admin and check the plan through the API:

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"tenantId":"226994","username":"admin","password":"123456"}' | jq -r .data.token)
curl -s "http://localhost:8080/system/user/page?pageNum=1&pageSize=10" -H "Authorization: $TOKEN"
curl -s "http://localhost:8080/system/role/page?pageNum=1&pageSize=10" -H "Authorization: $TOKEN"
```

The user list returns the tenant's single admin. The role list returns `{"code":403,...,"msg":"该功能不在您的套餐内，请联系管理员开通"}`.
