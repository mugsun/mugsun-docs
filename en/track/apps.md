# Integration

Integration manages tracking applications and their collection settings. Each application has an AppKey, which the frontend uses to initialize the SDK.

The page is under the Tracking menu and has five tabs:

| Tab | What it is for |
| --- | --- |
| Applications | Creating applications; changing the sample rate, retention and feature switches |
| Event definitions | Giving events a display name and an owner; disabling events you do not want |
| Sourcemaps | Uploading sourcemaps so that Error Monitoring can restore stacks |
| Visual rules | Adding click tracking to page elements without code changes |
| Integration health | Whether each application received events recently, and why something was rejected |

![The edit dialog of an application, with the sample rate, the data retention period and switches such as session replay in the form](/screenshots/track/track-app.png)

## Applications

Click "Add application"; only the app name is required. After saving, the "Application created" dialog appears with the AppKey and an integration snippet.

The AppKey is generated by the backend, starts with `ak_` and cannot be changed afterwards. The AppKey column of the list always shows it.

See [Your first event](/en/track/first-event) for wiring up the SDK with the AppKey.

### Application form

| Form item | Field | Values | Default | Notes |
| --- | --- | --- | --- | --- |
| App name | `appName` | Up to 64 characters | None | Required |
| Sample rate | `sampleRate` | 1 to 100 | 100 | A percentage, sampled by visitor. 100 collects everything |
| Enabled | `enabled` | On or off | On | When off, the collection endpoint rejects everything this application sends |
| Masked selectors | `maskSelectors` | CSS selectors separated by commas | Empty | Matching areas are not collected automatically and are not recorded in replays |
| Data retention period | `retentionDays` | 1 to 3650 days | 90 | How many days events are kept |
| Session replay | `replayEnabled` | On or off | Off | When on, the SDK starts recording |
| Replay sample rate | `replaySampleRate` | 0 to 100 | 10 | A percentage. 0 uploads only sessions in which an error occurred |
| Replay retention | `replayRetentionDays` | 1 to 30 days | 14 | How many days recordings are kept |
| API monitoring | `apiMonitorEnabled` | On or off | Off | Records the API requests the page sends |
| Response body capture | `apiBodyEnabled` | On or off | Off | JSON APIs only; credential endpoints are never captured |
| Response body masking | `apiBodyMaskEnabled` | On or off | Off | Replaces the values of personal data fields in response bodies with `***` |
| Response body retention | `apiBodyRetentionDays` | 1 to 30 days | 7 | How many days response bodies are kept |
| Precise location | `geoEnabled` | On or off | Off | With the user's consent, reports coordinates accurate to about 11 meters |
| Error alerting | `alertEnabled` | On or off | Off | Sends an in-app message when a new error appears or errors become frequent |
| Alert threshold | `alertThreshold` | 1 to 1000 | 10 | Alerts when one fingerprint reaches this count within 10 minutes |
| Remark | `remark` | Text | Empty | For notes only |

In the API, switch fields use `1` for on and `0` for off.

The following items appear only after the switch above them is on:

- Replay sample rate and Replay retention need Session replay.
- Response body capture needs API monitoring.
- Response body masking and Response body retention need Response body capture.
- Alert threshold needs Error alerting.

The details of each feature are on their own pages:

- Replay and API monitoring: see [Plugins](/en/track/plugins).
- Precise location: see [Spatial behavior](/en/track/spatial#get-coordinates-onto-events-first).
- Error alerting: see [Performance and errors](/en/track/perf-errors#error-alerting).

### When changes take effect

On the backend side they take effect immediately. After saving, the collection endpoint accepts or rejects by the new switches right away. With several backend instances, the other instances follow within 30 seconds.

On the browser side they wait for the SDK to fetch the settings again. The SDK fetches once at every start, and the fetched settings take effect at the next start.

See [Install & setup](/en/track/install#how-backend-settings-combine-with-code) for which one wins when an option is set both in the form and in code.

After an application is deleted, the collection endpoint no longer accepts what it sends.

## Event definitions

Events need no registration in advance. When an event name is reported for the first time, the backend adds a row here by itself. The event name cannot be changed, and rows cannot be added by hand.

The list is sorted by last reported, newest first, and can be filtered by event name and status. Four things can be changed:

| Item | Notes |
| --- | --- |
| Display name | A readable name for the event, up to 64 characters |
| Description | Up to 255 characters |
| Owner | Up to 64 characters |
| Status | Enabled or disabled |

After an event is disabled, the backend drops what is reported for it and records `EVENT_DISABLED` in Integration health. Data already stored is not affected.

Disabling takes effect immediately. With several backend instances, the other instances follow within 30 seconds.

The step dropdown of [Funnel Analysis](/en/track/funnel-retention) reads this table and lists at most 500 event names.

## Sourcemaps

Sourcemaps are the `.map` files in the build output, used to convert a stack from minified code back to positions in the source. See [Restoring the stack](/en/track/perf-errors#restoring-the-stack) for how they are used.

Click "Upload sourcemap", pick the application, enter the release and choose the file.

| Rule | Notes |
| --- | --- |
| File | `.map` only, up to 20 MB, and the content must be JSON with a `mappings` field |
| Release | Required, up to 128 characters. Only letters, digits and the three symbols `.` `-` `_` |
| File name | Up to 255 characters, with the same allowed characters as the release |
| Uploading again | A file with the same name under the same release replaces the earlier one |

The release must be exactly the same as `release` passed when the SDK is initialized. Error events find their sourcemaps by it.

The list, uploading and deleting on this tab all need `sys:track-app:edit`. With `sys:track-app:list` alone the list is not shown.

## Visual rules

See [Plugins](/en/track/plugins#visual-tagging) for the complete steps of visual tagging. This tab takes care of three things:

- Click "Start visual selection" and enter the address of the target page. The page opens in a new window in selection mode.
- An element picked on the page first becomes a draft. Click Confirm and enter an event name to turn it into a rule, or click Discard to delete it.
- In the rule list you can edit, disable and delete rules. The selector cannot be changed.

The target address must start with `http://` or `https://`. The event name must start with a letter, may only use letters, digits and underscores, and is up to 64 characters.

| Limit | Value |
| --- | --- |
| Lifetime of the selection token | 30 minutes |
| Drafts in one selection | Up to 50 |
| Rules sent out for one application | Up to 200 |
| Selector | Up to 512 characters |
| Match text | Up to 128 characters |

The selection token lives only in the memory of this admin console page. After a reload the token is gone and you start the selection again.

A confirmed rule is sent out right away and takes effect at the client's next start. An empty route means the whole site, and an empty match text means any text.

## System parameters

The parameters below apply to every application. Change them under System Settings → Parameters; see [Dictionaries and parameters](/en/boot/features/dict#read-and-write-parameters).

| Parameter key | Default | What it does |
| --- | --- | --- |
| `track.collect.rate-limit` | `600` | How many times per minute one IP may report to one application. The limit for replay uploads is twice this |
| `track.collect.batch-max` | `100` | How many events one report may carry. The rest is cut off |
| `track.replay.session-max-bytes` | `20971520` | The total replay size of one session |
| `track.api-body.max-bytes` | `1048576` | The size limit of a single response body |
| `track.storage.daily-max-bytes` | `10737418240` | Replays and response bodies added per day on the whole platform |
| `track.storage.app-daily-max-bytes` | `2147483648` | Replays and response bodies added per day by one application |
| `track.storage.min-free-bytes` | `5368709120` | Receiving replays and response bodies pauses when the free space on the storage disk is below it |

The last five parameters are in bytes. Reports beyond a limit are rejected or cut off, and the matching reason code shows up in Integration health.

## Permissions

| Permission | What it allows |
| --- | --- |
| `sys:track-app:list` | Opening Integration and seeing Applications, Event definitions and Integration health |
| `sys:track-app:add` | Adding applications |
| `sys:track-app:edit` | Editing and deleting applications, changing event definitions, using the Sourcemaps tab |
| `sys:track-visual:list` | Seeing Visual rules |
| `sys:track-visual:edit` | Starting a selection, handling drafts, editing and deleting rules |

You only see the applications of your own tenant.

## API

All endpoints are under `/system/track` and require a login. Write operations use POST with a JSON request body, except uploading a sourcemap.

| Method and path | Permission | Notes |
| --- | --- | --- |
| `GET /app/page` | `sys:track-app:list` | Pages of applications, optionally filtered by `appName` |
| `POST /app/submit` | See below | The request body holds the fields of the application form. With `id` it is an edit |
| `POST /app/remove` | `sys:track-app:edit` | The request body holds `id` |
| `GET /event-def/page` | `sys:track-app:list` | `appKey` is required. Optionally filtered by `eventName` and `status` |
| `POST /event-def/submit` | `sys:track-app:edit` | Changes the display name, description, owner and status |
| `POST /sourcemap/upload` | `sys:track-app:edit` | A form upload with the fields `file` `appKey` `release` |
| `GET /sourcemap/page` | `sys:track-app:edit` | Optionally filtered by `appKey` and `release` |
| `POST /sourcemap/remove` | `sys:track-app:edit` | The request body holds `id` |
| `GET /visual/rule/page` | `sys:track-visual:list` | Optionally filtered by `appKey` and `status` |
| `POST /visual/rule/submit` | `sys:track-visual:edit` | Changes the event name, route, match text and status |
| `POST /visual/rule/remove` | `sys:track-visual:edit` | The request body holds `id` |

`/app/submit` needs `sys:track-app:add` to add and `sys:track-app:edit` to edit. A successful add returns the complete application, including the generated `appKey`.

Every paged endpoint accepts `pageNum` and `pageSize`; `pageSize` defaults to 10.

The selection flow also uses several endpoints under `/visual/token` and `/visual/drafts`, all of which need `sys:track-visual:edit`.

See [Your first event](/en/track/first-event#integration-health) for the two Integration health endpoints.
